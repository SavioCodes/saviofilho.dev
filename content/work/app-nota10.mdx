## Context

I wanted one project in the portfolio that looked like a real product, not an API demo. Nota10 became the vehicle for that: a study workflow where a student uploads source material and receives summaries, flashcards, exam-style questions, and a spaced-review queue.

## Problem

Most "AI study app" projects stop at prompt orchestration. I wanted the harder layer: ingestion, document state transitions, deterministic chunking, generation caching, and review scheduling that would still make sense if the model changed underneath.

## Constraints

- The same repository needed to support mobile and web clients.
- Generated content had to stay traceable back to source chunks.
- The review queue needed idempotent sync behavior per user and artifact.
- Setup needed to be reproducible enough for CI and another engineer.

## Architecture

```text
client (Expo Router)
  -> typed procedures (tRPC)
  -> Express API
  -> domain services
  -> Postgres / storage / AI providers
```

The pipeline is explicit:

```text
upload
  -> extracting
  -> normalized text
  -> deterministic chunks
  -> artifact generation
  -> validation against source hash
  -> review queue sync
  -> ready
```

## Decisions and trade-offs

- I kept tRPC because the repo benefits from shared contracts more than it needs open interoperability.
- I used explicit chunk hashes and generation modes because that creates room for caching and auditability later.
- I kept billing and webhook hooks in the environment model, even though they are not the center of the product, because production-shaped boundaries make the project stronger.

## What worked

- The repo now communicates a clear product shape: client, API, data layer, docs, tests, and runbook.
- The README and docs make the project interview-friendly because the architecture is explainable.
- The runbook covers the exact incidents I would expect in a real setup: database config, OAuth callbacks, generation failures, and billing webhooks.

## What is still incomplete

- The public repo still needs a live deployed version before it can serve as a full product showcase.
- I removed tracked `.env.production` and `.env.staging` files because they weakened the repository's security posture even as placeholders.
- The strongest next improvement is a short demo capture showing the full `login -> upload -> generate -> review` loop.
